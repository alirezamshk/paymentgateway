# راهنمای فارسی سرویس پرداخت مرکزی

این سند خلاصهٔ فارسی برای راه‌اندازی، بهره‌برداری و اتصال سایت‌هاست. جزئیات فنی کامل در
اسناد انگلیسی همین پوشه آمده است:

| سند | موضوع |
|-----|-------|
| [CPANEL.md](../CPANEL.md) | نصب مرحله‌به‌مرحله روی cPanel (همان روشی که روی سرور اصلی اجرا شد) |
| [PROVIDERS.md](../PROVIDERS.md) | نکات هر درگاه (سپهر، زرین‌پال، سپرده، آسان‌پرداخت) |
| [TROUBLESHOOTING.md](../TROUBLESHOOTING.md) | خطاهای رایج و راه‌حل |
| [INTEGRATION.md](../INTEGRATION.md) | راهنمای برنامه‌نویس سایت‌های متصل (امضا، وب‌هوک، نمونه‌کد) |
| [openapi.yaml](../openapi.yaml) | مستند کامل API |

## سیستم چه کار می‌کند؟

```text
سایت مشتری ──(API امضاشده)──▶ سرویس پرداخت ──▶ مرچنت آن سایت ──▶ درگاه بانکی
                                   ▲                                   │
                                   └── بازگشت مشتری + تایید از سرور ◀──┘
سایت مشتری ◀── وب‌هوک امضاشده (با تلاش مجدد) ─── سرویس پرداخت
```

* هر سایت یک **کلاینت** است با کلید و secret مخصوص خودش.
* هر کلاینت یک یا چند **مرچنت** دارد؛ هر مرچنت یعنی حساب/ترمینال آن سایت نزد یک درگاه.
  پول مستقیم به حساب همان مرچنت واریز می‌شود.
* سایت‌ها هیچ‌وقت مستقیم با بانک کار نمی‌کنند و اطلاعات درگاه را نمی‌بینند.
* پرداخت فقط وقتی «موفق» می‌شود که سرور خودش از بانک تایید (verify/advice) بگیرد؛ پارامترهای
  آدرس بازگشت ملاک نیستند.

## وضعیت درگاه‌ها

| درگاه | وضعیت |
|-------|-------|
| سپهر (صادرات) | ✅ پرداخت واقعی موفق؛ اتصال کامل پنل فاکتور (v2moon) با وب‌هوک تایید شد |
| زرین‌پال | ✅ تست Sandbox موفق — تست واقعی با merchant_id اصلی باقی است |
| سپرده | آماده — نیاز به یک تست واقعی |
| آسان‌پرداخت | آماده — نیاز به اطلاعات حساب و تست واقعی |

قبل از استفادهٔ واقعی از هر درگاه، یک پرداخت با مبلغ کم انجام دهید.

## نصب (خلاصه)

مراحل کامل با همهٔ دستورها در [CPANEL.md](../CPANEL.md) است. نکات کلیدی که در نصب واقعی به آن‌ها برخوردیم:

1. با **root** کار نکنید؛ با کاربر سایت وارد شوید: `su -s /bin/bash - USER`
2. PHP پیش‌فرض سرور ممکن است قدیمی باشد؛ در هر جلسهٔ SSH:
   `export PATH=/opt/cpanel/ea-php83/root/usr/bin:$HOME/bin:$PATH`
3. اگر `getcomposer.org` باز نمی‌شود، Composer را از GitHub دانلود کنید (مرحلهٔ ۴ راهنما).
4. رمز دیتابیس را دستی تایپ نکنید؛ با `uapi` بسازید و مستقیم در `.env` بنویسید (مرحلهٔ ۶).
5. **مقدار `APP_KEY` را در جای امن نگه دارید.** بدون آن همهٔ secretها و اطلاعات درگاه‌ها غیرقابل‌بازیابی است.
6. اگر DNS دامنه روی Cloudflare است و دسترسی ندارید، نصب در **پوشه** (`/payment`) بدون تغییر DNS کار می‌کند.
7. پوشهٔ `payment` باید `.htaccess` خودش را با `AddHandler ... ea-php83` داشته باشد تا سایت اصلی (مثلاً وردپرس با PHP 7.4) دست نخورد.
8. Cron هر دقیقه با **مسیر کامل PHP 8.3** اجرا شود.

## کار با پنل مدیریت

آدرس: `https://tech-kala.com/payment/admin` (زبان پنل با `ADMIN_LOCALE=fa` فارسی است.)

### اضافه کردن یک سایت جدید
1. **سایت‌ها ← سایت جدید**: نام، شناسهٔ کوتاه انگلیسی، آدرس وب‌هوک و آدرس بازگشت (هر دو HTTPS).
2. سه مقدار **شناسهٔ کلاینت (۳۰ کاراکتر)**، **Client secret (۶۹ کاراکتر)** و **Webhook secret**
   فقط یک بار نمایش داده می‌شوند. آن‌ها را امن به برنامه‌نویس سایت بدهید.
3. در صفحهٔ همان سایت **افزودن مرچنت**: درگاه و اطلاعات حساب (برای سپهر فقط شماره ترمینال)
   و تیک «مرچنت پیش‌فرض». سپس **تست اطلاعات حساب**.
4. سند [INTEGRATION.md](../INTEGRATION.md) را برای برنامه‌نویس سایت بفرستید.

### کارهای روزمره
* **پرداخت‌ها**: جستجو با شناسهٔ پرداخت، شماره سفارش یا کد پیگیری. در صفحهٔ هر پرداخت،
  بخش **تاریخچه** همهٔ مراحل را نشان می‌دهد.
* پرداخت‌هایی که در وضعیت «بازگشت از درگاه» یا «در حال تایید» مانده‌اند هر ۵ دقیقه خودکار
  دوباره بررسی می‌شوند؛ دکمهٔ **اجرای مجدد تایید از درگاه** هم هست.
* **وب‌هوک‌ها**: وب‌هوک‌های ناموفق را بعد از رفع مشکل سایت مقصد با **ارسال مجدد** بفرستید.
* **تعویض کلید سایت**: «ساخت کلید جدید» ← قرار دادن در سایت ← «باطل کردن» کلید قدیمی.
* **لاگ ممیزی**: ورودها، تغییرات و تلاش‌های ناموفق احراز هویت (`client.auth_failed`).

## تست سریع بعد از نصب یا تغییر

روی سرور (با کاربر سایت):

```bash
cd ~/paymentgateway
export PATH=/opt/cpanel/ea-php83/root/usr/bin:$HOME/bin:$PATH
export TK_BASE_URL=https://tech-kala.com/payment
export TK_KEY_ID=$(php artisan tinker --execute='echo App\Models\ClientCredential::where("status","active")->latest("id")->value("key_id");')
export TK_SECRET=$(php artisan tinker --execute='echo App\Models\ClientCredential::where("status","active")->latest("id")->first()->secret();')
php scripts/test-client.php create              # باید HTTP 201 و وضعیت pending بدهد
php scripts/test-client.php status pay_...       # بعد از پرداخت: paid
```

`payment_url` را در مرورگر باز کنید و **VPN را خاموش کنید** (درگاه‌های شاپرک IP خارجی را رد می‌کنند).

## نکات مهم درگاه سپهر

* آدرس API: `https://sepehr.shaparak.ir/Rest/V1/PeymentApi/...` روی پورت ۴۴۳
  (پورت قدیمی 8081 اتصال را رد می‌کند).
* **IP سرور باید نزد سپهر ثبت باشد**؛ در غیر این صورت خطای `-2`.
* سپهر بررسی می‌کند مشتری از دامنهٔ ثبت‌شده آمده باشد (خطای `UrlReferrer`). صفحهٔ پرداخت فقط
  دامنه را می‌فرستد (`Referrer-Policy: origin`)، پس دامنهٔ `APP_URL` باید همان دامنهٔ ثبت‌شده باشد.

## خطاهای رایج

| خطا | علت | راه‌حل |
|-----|-----|-------|
| `AUTH_INVALID_SIGNATURE` | کلید/secret اشتباه کپی شده یا مسیر امضا ناقص | طول‌ها: کلید ۳۰، secret ۶۹. مسیر کامل با `/payment` امضا شود |
| `GATEWAY_UNAVAILABLE` | سرور به درگاه وصل نمی‌شود | با `curl` از سرور تست کنید؛ آدرس/پورت/فایروال |
| `SEPEHR_-2` | IP سرور نزد سپهر ثبت نیست | ثبت IP نزد پشتیبانی سپهر |
| `UrlReferrer` در صفحهٔ سپهر | دامنهٔ ارجاع ثبت‌نشده یا کد قدیمی | `git pull` و یکسان بودن دامنه با دامنهٔ ثبت‌شده |
| `Access denied` دیتابیس | رمز اشتباه در `.env` | تنظیم رمز با `uapi` (CPANEL.md مرحلهٔ ۶) |
| وب‌هوک‌ها در صف می‌مانند | Cron اجرا نمی‌شود | بررسی Cron و `QUEUE_WORK_VIA_SCHEDULER=true` |

فهرست کامل: [TROUBLESHOOTING.md](../TROUBLESHOOTING.md)

## امنیت — یادآوری
* secretها و `APP_KEY` را هرگز در چت، ایمیل یا گیت قرار ندهید.
* کلاینت تستی را بعد از اتمام تست غیرفعال کنید.
* بعد از راه‌اندازی، فایل‌های قدیمی پرداخت در `public_html` (مثل `sepehr2`) را غیرفعال کنید؛
  آسیب‌پذیری XSS دارند و به `tikpgate.com` وابسته‌اند.
